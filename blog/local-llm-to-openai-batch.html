I Built a Local LLM Rig to Escape API Bills. Then I Paid OpenAI Again.

By TaeHo Kim (Hannune)  ·  Published June 13, 2026

I spent a year telling people I left the cloud LLM bill behind. Last week I started paying OpenAI again. Not all of it. One specific lane, on purpose.

What workload pulled me back

The lane is the one inside 2asy.ai that reads thousands of corporate filings from OpenDART (Korea), EDINET (Japan), HKEX (Hong Kong), and CNINFO (China), and turns them into entities and relations for a Neo4j knowledge graph. There is one rule I will not bend on. Each filing gets its own isolated LLM call. The model never sees more than one document at a time. That rule exists because I have already paid the price for breaking it.

So the question for a solo operator was never which model is smartest. It was which provider can actually run thousands of strictly isolated single-document calls in parallel, cheaply, with strict JSON schemas, without melting and without leaking content between docs.

Option 1: stay fully local on the RTX 4090 and the W6800

My local rig runs Gemma 4 26B as a multimodal MoE on port 31002, served by llama.cpp from a Q4 GGUF. It is great for live chat. It is fine for the demos at demo.hannune.ai. It is not good enough for unattended thousands-of-docs extraction with a strict schema and a deadline.

I tried to put the same model on vLLM for throughput and hit two walls back to back. The 4-bit MoE has no expert-mapping path implemented in vLLM, so the cheap quantized weights cannot actually be loaded. On top of that, the vLLM container demanded CUDA 12.9 while my host driver is on 12.8, and this is the production GPU server. I was not pushing a driver upgrade just to test a batch lane. Even on llama.cpp, the server has crashed once on a CUDA graph optimization, and I now keep GGML_CUDA_DISABLE_GRAPHS=1 in my back pocket as a recovery flag.

Local stays in the stack. It is just not where the batch lane runs.

Option 2: OpenRouter

The pitch is fine. Dozens of models behind one key, easy to switch providers, useful for testing.

The problem for this workload is simple. OpenRouter has no real batch API. Every request runs at live inference pricing, so the cost story does not improve over a normal API call. On top of that, in my own runs on a flash-class model with concurrency 32 I saw per-call latency swing between two seconds and seventeen seconds, with occasional 121-second timeouts and 429 rate-limit responses. A router adds a hop and a variable upstream provider, and that variability lives in the tail of your latency distribution. For interactive UI calls, fine. For unattended jobs that run overnight, the tail is the cost.

Option 3: Gemini batch (the painful one)

This is the option I would rather not have learned the hard way.

Gemini publishes a batch API. On paper, exactly the cheap and isolated lane I needed. In practice, the SDK path I used ran my "batch" by stitching multiple requests into a single context window and asking the model to produce one combined response. That is not a batch in the sense I needed. That is multi-document attention by another name, which is exactly what my isolation rule was written to prevent.

The failure showed up downstream, not in the SDK logs. Extracted entities and relations started carrying content from neighboring documents in the same batch line. By the time I noticed, the Neo4j graph and the entity registry had absorbed a meaningful share of fabricated entries. I rolled both back to a clean pre-batch snapshot, then spent a day reconciling what had to be re-extracted.

The underlying behavior is tracked publicly in the Google SDK issue queue as known and marked "not planned" upstream. The operator-level takeaway is short. A "batch" endpoint is not automatically isolated. The marketing copy says batch. The semantics may be inline concatenation. Verify which one you actually have before you point it at a production graph.

Option 4: OpenAI Batch API, which finally fit

The OpenAI Batch API works the way I needed a batch API to work. You upload a JSONL file. Each line is a fully independent request with its own messages and its own response schema. The service runs them as separate calls, with no shared context, returns the results in another JSONL, and discounts the whole job by 50 percent against live pricing. The published completion window is up to 24 hours. My own jobs have come back much faster.

For the binary signal gate I run before extraction, a recent 100-document gpt-5.4-nano batch came back in about 2.7 minutes. Zero 429s. Zero failed lines. For the heavier extraction step I use gpt-5.4-mini with a strict JSON schema for entities, events, and relations. Per-document cost on my runs lands close to a cent.

The win was not raw price per token. The win was that batch isolation and strict JSON schemas and reasonable tail latency all landed in the same product, on the same request, with no router in between.

This is not an anti-local post

I have to be straight about the tension with what I have written before. My consulting page still talks about cutting cloud LLM bills with local infrastructure, and I still believe that for steady single-stream serving on my own hardware, for the multimodal work, for the live demos at demo.hannune.ai, and for anything I do not want to send out. The 4090 and the W6800 are not going anywhere.

What changed is that I stopped treating "local first" as a single rule for the whole business and started treating it as one option per pipeline. The batch extraction lane left the house. The rest of the stack stayed.

If you are picking infrastructure for a one-person AI shop

The question is not local versus cloud. The questions that actually matter are more specific than that. How spiky is the workload over a real week. Where exactly does the isolation boundary need to sit, per request or per document or per session. Does the provider's batch endpoint truly run the requests independently, or does it concatenate them under the hood. What does the tail of your latency distribution look like under your real concurrency, not the marketing concurrency. And when the model gets something wrong in a way that looks correct, what happens to your graph or your output store before you notice.

Answer those per pipeline. For me, this month, the answer is a hybrid. Local for serving and multimodal. OpenAI Batch for the extraction lane that has to be isolated and cheap at scale. The mix will shift the next time a workload shifts.
