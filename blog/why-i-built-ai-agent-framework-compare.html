Why I built an AI agent framework comparison directory

By TaeHo Kim (Hannune)  ·  Published June 26, 2026

I have been building production LLM systems for seven years. The last two of those were almost entirely about agents. I picked LangGraph for one project, CrewAI for another, Pydantic AI for a third, and shipped a fourth on the OpenAI Agents SDK. Each choice took two weeks of reading and one ugly migration to undo. This week I shipped an AI agent framework comparison directory so the next engineer does not have to repeat that.

The choice that wasted two weeks every time

"Which agent framework should I use?" is a question that does not have a single answer. It has fifteen answers, and the right one depends on whether you need a graph, a crew, a conversation, or just typed tool calls. LangGraph wants you to draw your agent as an explicit state machine. CrewAI wants you to think in roles. AutoGen wants conversational message-passing. Pydantic AI wants typed I/O on top of a thin LLM client. OpenAI Agents SDK wants you inside the OpenAI runtime. They are not interchangeable. Picking the wrong one costs a rewrite.

For each of my four agent projects I lost roughly two weeks reading docs, building toy demos, and arguing with myself about state models and human-in-the-loop primitives before I picked. The information I needed each time was a side-by-side table. Control style. State model. Use case fit. License. GitHub stars as a crude liveness signal. There was no good one.

The closest things were scattered blog posts and one or two old Twitter threads. The frameworks all describe themselves as the right choice. None of them tell you when they are the wrong choice.

Why a directory, not another framework

The default solo-builder instinct in 2026 is to ship another agent framework. I almost did. I have strong opinions about state models and I have shipped real ones in production. But a sixteenth framework would be a worse product than the fifteen that already exist, because the bottleneck is not framework supply. The bottleneck is decision support.

The other reason I did not ship a framework: foundation labs are absorbing the agent layer horizontally. OpenAI Agents SDK, Anthropic's tool use, Google's agent stack. If your moat is a thin abstraction over an LLM client, a foundation lab can copy it in a quarter. The product surface that survives is not another framework. It is the comparison data itself: the slot-by-slot facts about how fifteen real frameworks behave, kept current weekly. A foundation lab does not want to be in the business of recommending its competitors. A comparison directory does.

I am running the same play that OpenAlternative ran for self-hosted open-source software. One person, one narrow niche, a directory product that compounds with traffic and data. They reached six-figure ARR with that pattern. The narrower the niche, the cleaner the moat. AI agent frameworks are narrower than open source alternatives.

What is in the directory

Fifteen frameworks at launch: LangGraph, CrewAI, AutoGen, Pydantic AI, OpenAI Agents SDK, Mastra, LangChain Agents, LlamaIndex Agents, Semantic Kernel, Haystack Agents, Smolagents, Atomic Agents, Phidata, DSPy, and AG2. For each one: control style, state model, primary language, license, GitHub star magnitude, first release year, and a short list of use cases the framework is actually shaped for. A short tagline that I would write to a friend, not a tagline lifted from the marketing site.

The page is live at compare-lab.xyz/ai-agent-frameworks/. It is a single side-by-side view that loads fast and renders without JavaScript for the comparison table. I am keeping the data file open in the repo so corrections from people who know one of these frameworks better than I do are easy to land.

What I am not claiming

I am not claiming a benchmark. There is no agent reasoning score on this page, because I do not believe in the public agent benchmarks that exist today. They measure tool-call success on toy tasks and miss the things that actually decide a project, which are state-model fit, escape hatches, and how the framework behaves when something breaks. The directory is a facts-and-shape comparison, not a leaderboard.

I am also not claiming any of the frameworks are bad. Each of the fifteen has a use case where it is the right pick. The directory tries to make those use cases obvious, not to rank.

What happens over the next 30 days

I am treating this as a 30-day test. Three signals I am watching:

  • Organic traffic to compare-lab.xyz/ai-agent-frameworks/*, measured through Search Console and analytics. The narrow keyword set is "AI agent framework comparison", "LangGraph alternative", "CrewAI alternative", and similar shape.
  • Inbound on the directory itself. DMs, comments, contact-form notes from people who saw the page and either want a framework added or want to argue about my use-case classification. Engagement is the leading indicator before sponsored placements become a real conversation.
  • Consulting inbound. Hannune is a Graph RAG and AI agent consulting practice. If the directory pulls one well-fit lead in the first 30 days, the project earns its operating cost many times over even before any directory monetization.

If two of the three land, the framework pool expands from fifteen to twenty-plus and the weekly GitHub data refresh becomes a cron, not a manual run. If none of the three land, I write a short post-mortem and move on. The directory pattern is the bet, not the specific topic.

What this is part of

This directory is one of several narrow comparison pages I am shipping under compare-lab.xyz. Each one targets a specific decision a solo or small team has to make: pick an agent framework, pick an AI headshot generator, pick a vertical SaaS template, pick a metrics dashboard. The thesis is the same in all of them. Comparison data is a product. The first one out the door is the AI agent framework directory because it is the question I have answered most often for other engineers, and the one I wanted to stop answering by hand.

If you have shipped an agent in production on a framework I have on the list, and the data file gets one of your details wrong, the repo is open and a one-line correction is welcome. If you have shipped on a framework I do not yet list, send me the slug and I will evaluate it for the next batch.
